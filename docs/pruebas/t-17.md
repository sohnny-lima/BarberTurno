## Implementación

- core/modelos/catalogo.ts: modelos espejo y unión excluyente de alta nueva o vínculo ADMIN.
- core/api/ServiciosApi y BarberosApi: listas, altas, edición y estado; URLs relativas y HttpClient.
- features/admin/servicios y barberos: tablas de Material, incluirInactivos, carga/error/vacío, diálogos y confirmación. Precios es-PE/PEN con S/ y dos decimales.
- ServicioDialogo: formulario reactivo tipado, validación UX de nombre/descripción/duración/precio; edición y alta.
- BarberoDialogo: cuenta nueva, vínculo por usuarioId con aviso de T-31, edición sin correo/contraseña, botón Generar con crypto.getRandomValues, entrega de contraseña después de cerrar el alta y borrado del campo.
- PasswordTemporalDialogo: presentación una sola vez, copia explícita y comunicación presencial; nunca almacenamiento web ni logs.
- Validadores: duración 10–180/múltiplo de diez, precio 0–999999.99/hasta dos decimales, RN-25 en caracteres y bytes; generador ASCII de 16 caracteres con muestreo por rechazo y mezcla.
- shared/formulario: NOMBRE_DUPLICADO al campo nombre; se conserva el mapeo de CORREO_DUPLICADO y de errores[] por campo.
- ConfirmarEstadoDialogo: la operación comienza al confirmar; evita solicitudes dobles, muestra errores y el número de reservas futuras recibido. Un aviso posterior exige Cerrar, que devuelve true para recargar la tabla.
- Rutas lazy reales /admin/servicios y /admin/barberos con authGuard y rolGuard ADMIN.
- catalogo.scss: desplazamiento horizontal dentro de una región etiquetada y enfocada a 360 px.
- catalogo-dialogo.scss y subscriptSizing dinámico: ancho y separación de campos encapsulados, espacio para ayudas y errores de varias líneas.
- README: funcionalidad de catálogo y ejecución del nuevo recorrido.
- Backend intacto. No se añadió ni modificó Javadoc porque no se cambió ninguna clase Java; el verify existente sigue comprobándolo estrictamente.

## Recorrido HTTP y visual real

El script requiere una BD dev sin usuarios y puertos libres, para identificar exclusivamente la cuenta ADMIN creada por el ensayo.
La clave de conexión se carga solo en PGPASSWORD del proceso desde BT_DB_PASSWORD del archivo local, sin imprimirla.
BT_ADMIN_CORREO, BT_ADMIN_PASSWORD y BT_ADMIN_NOMBRE se generan con valores ficticios en el entorno de ese proceso
(el correo acaba en @ejemplo.test; la contraseña combina letra, dígito y un GUID) y se restauran en finally.
El backend dev hereda esas variables e inicializa el ADMIN. No hay credenciales fijas ni valores locales en el repositorio o en esta evidencia.

Start-Process usa ventanas ocultas. Backend dev y ng serve sirven el proxy /api en localhost:4200.
WebRequestSession conserva las cookies; GET sesión emite XSRF-TOKEN y las escrituras usan X-XSRF-TOKEN.
Se comprueba login ADMIN, altas, listados, edición, desactivación/reactivación de ambos recursos,
exclusión del barbero inactivo del listado activo y logout. En las seis rutas POST/PUT/PATCH
se exige 403 con sesión ADMIN válida sin CSRF y con CSRF incorrecto: doce rechazos reales.
La autorización CLIENTE/BARBERO sigue cubierta por las pruebas de integración de T-13/T-14 incluidas en las 896;
no se creó ningún endpoint nuevo ni se tocó SecurityConfig.


Una única línea SQL se trataba como string y [0] tomaba un carácter; se fuerza @(...)[0] antes de convertir a long.

Limpieza limitada de id=2 explicada arriba; los siguientes ensayos y el final confirmaron todos los DELETE.

8. Medición visual inicial incluía la barra vertical en el ancho esperado:

~~~text
AssertionError [ERR_ASSERTION]: La página desborda horizontalmente

~~~

Se conserva la comprobación del contenedor dentro del viewport y contenido de tabla mayor que su ancho visible.

9. Revisión visual: ayudas de varias líneas se superponían con Generar; luego se observó que Material sobreescribía
la distribución global del formulario. Se aplicó subscriptSizing dinámico y estilos encapsulados compartidos;
la comprobación visual exige espacio entre campos y ayuda separada de Generar. No se cambió negocio.

10. Al añadir el script nuevo, Git avisó: CRLF will be replaced by LF the next time Git touches it.
La regla amplia de frontend/.gitattributes heredada de T-12 imponía LF a todos los .ps1 y contradecía
la raíz y este encargo. Se retiró esa regla (sin añadir otra); ahora el script nuevo tiene w/crlf,
i/lf canónico de Git y attr/text eol=crlf. El script de T-12 no se modificó; futuros checkouts heredan CRLF.
