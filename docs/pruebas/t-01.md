Las dos ejecuciones completas usaron el cliente previsto, autenticación local y el mismo SQL versionado:

```powershell
$env:PGPASSFILE = Join-Path (Get-Location) '.local/pgpass.conf'
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -X -w -h localhost -p 5433 -U postgres -d postgres -f tools/db-local.sql
```

Resultado de ambas ejecuciones:

```text
       base       | propietario
------------------+-------------
 barberturno      | barberturno
 barberturno_test | barberturno
(2 rows)
```

El SQL usa `ON_ERROR_STOP`, comprueba PostgreSQL 18 y el puerto 5433 antes de escribir, valida los objetos existentes y crea únicamente los faltantes. Solicita la contraseña mediante `\password` solo si falta. Una base existente con otro propietario o un rol con permisos incompatibles produce un error para revisión, conservando los objetos. No contiene contraseñas ni instrucciones de cambio de dueño.

Incidencias de ejecución resueltas:

- La conexión inicial falló con código 1 (`fe_sendauth: no password supplied`). El primer archivo pgpass estaba vacío; tras guardarlo el usuario, la autenticación mediante `PGPASSFILE` funcionó. No se mostró su contenido.
- El primer intento de creación quedó esperando el prompt nativo de Windows y se detuvo al alcanzar 30 segundos. El rol quedó sin contraseña, por lo que el script volvió a solicitarla al reintentar. Para la primera ejecución completa se usó un proceso sin ventana, entrada redirigida y `OSTYPE=msys` únicamente en ese proceso, enviando dos veces la misma contraseña local sin imprimirla. Este modo usa el fallback a stdin previsto por [el código oficial de PostgreSQL 18](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/common/sprompt.c). El reintento y la segunda ejecución terminaron con código 0; el SQL no se debilitó.
- El ejecutor aislado dejó de poder crear procesos después de inicializar Git (`setup refresh had errors`). Las verificaciones posteriores se ejecutaron con el usuario local mediante escalación aceptada. `.git` quedó a nombre del usuario del sandbox y Windows denegó reasignar su dueño. Se registró exclusivamente `D:/Proyectos/BarberTurno` como `safe.directory` en la configuración global del usuario; Git funciona normalmente sin desactivar la protección para otras rutas.

El cliente del PATH apunta a la instalación 17; el README indica la ruta explícita del 18. La instalación real 18.0 difiere del parche 18.6 citado en arquitectura §2; se registra para el arquitecto sin cambiar esos documentos ni la tecnología. Las instantáneas y los secretos locales están bajo `.local/`, ignorada por Git.

No quedan criterios pendientes ni bloqueos de T-01. Su estado, fecha y hash base figuran en [tareas.md](../tareas.md); el commit posterior de cierre guarda estas evidencias y la documentación final. T-02 y T-03 no se implementaron.
