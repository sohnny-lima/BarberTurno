## Causa y comprobación de la API

El defecto confirmado es la renovación automática por `CsrfAuthenticationStrategy` en cada petición autenticada con JWT y API STATELESS. Una cabecera CSRF leída antes de otra petición deja de coincidir con la cookie que actualiza el navegador.

Se inspeccionaron los JAR locales de Spring Security **7.1.1** con `javap` de JDK **21.0.8**:

```powershell
$javap = 'C:/Program Files/Eclipse Adoptium/jdk-21.0.8.9-hotspot/bin/javap.exe'
& $javap -c -p -classpath C:/Users/limas/.m2/repository/org/springframework/security/spring-security-config/7.1.1/spring-security-config-7.1.1.jar org.springframework.security.config.annotation.web.configurers.CsrfConfigurer
& $javap -c -classpath C:/Users/limas/.m2/repository/org/springframework/security/spring-security-web/7.1.1/spring-security-web-7.1.1.jar org.springframework.security.web.authentication.session.NullAuthenticatedSessionStrategy org.springframework.security.web.csrf.CookieCsrfTokenRepository
```

API verificada: `CsrfConfigurer.sessionAuthenticationStrategy(SessionAuthenticationStrategy)`; `getSessionAuthenticationStrategy()` devuelve la estrategia configurada antes de crear la predeterminada `CsrfAuthenticationStrategy`. `configure()` la añade mediante `SessionManagementConfigurer.addSessionAuthenticationStrategy`. `NullAuthenticatedSessionStrategy.onAuthentication(...)` solo retorna: basta sustituir la estrategia del configurador CSRF; no hace falta cambiar la política STATELESS ni la estrategia global de sesiones.

También se verificó `CookieCsrfTokenRepository.saveToken(null, request, response)`: emite cookie vacía con Max-Age=0 y aplica el mismo `cookieCustomizer`; la siguiente petición sin cookie genera un token mediante el manejador SPA.

## Cambio mínimo

- `SecurityConfig`: expone el mismo `CookieCsrfTokenRepository` como bean para compartirlo con autenticación, con `withHttpOnlyFalse()` y el `cookieCustomizer` original. Configura exclusivamente `csrf(...).sessionAuthenticationStrategy(new NullAuthenticatedSessionStrategy())`. Conserva `spa()`, `DEFAULT_CSRF_MATCHER`, STATELESS, resolutor JWT, permisos y resto de la cadena.
- `AuthController`: después de un login o registro exitoso, y en logout público/idempotente, llama a `saveToken(null, peticion, respuesta)`. Elimina XSRF-TOKEN con los mismos atributos. El siguiente `GET /api/auth/sesion` que ya hace la SPA emite uno nuevo; una petición autenticada con token existente lo conserva. Un fallo de credenciales no invalida el token. No se alteran rutas, DTO, códigos ni reglas.
- `AuthIT`: nueve casos nuevos de DA-26 reutilizan exactamente el contexto existente y capturan el logger de `CsrfAuthenticationStrategy` sin introducir otro contexto; restauran nivel y appender en `finally`. El caso de GET incluye un fragmento JS ausente (404, atraviesa los filtros de recursos estáticos) y comprueba ausencia de Set-Cookie XSRF. La escritura aplica las cookies de cada respuesta antes de enviar la cabecera inicial: reproduce el desfase real, en lugar de conservar artificialmente la cookie vieja. Tras login/registro el token anterior se rechaza frente a la nueva cookie (403) y el nuevo funciona (204).
- `AuthCookieSecureIT`: amplía el caso existente para comprobar invalidación de XSRF con Secure, emisión posterior y conservación en cambio de contraseña. Mantiene `DirtiesContext(AFTER_CLASS)` preexistente.

Javadoc útil añadido/actualizado: clases `SecurityConfig` y `AuthController` con versión, método bean `csrfTokenRepository` (propósito, política y parámetro/retorno), `securityFilterChain` (DA-26 y repositorio), constructor de `AuthController` y métodos `sesion`, `registrar`, `login`, `logout` (momento de invalidación, parámetros servlet y respuesta). No hay nuevos métodos públicos sin documentación.
