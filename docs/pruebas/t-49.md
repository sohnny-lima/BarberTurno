# T-49 · Token CSRF estable durante la sesión

Fecha: 06/10/2026. Encargo 059, DA-26. Rama `tarea/T-49-diagnostico-403`.
Estado: En curso; corrección y revisión independiente pendientes. Sin merge ni push, conforme a la precisión del arquitecto.
Base: `4ea359e`, documentación `c9b57eb`, arnés E2E `01ba025` (preexistentes).

## Causa y comprobación de la API

El defecto confirmado es la renovación automática por `CsrfAuthenticationStrategy` en cada petición autenticada con JWT y API STATELESS. Una cabecera CSRF leída antes de otra petición deja de coincidir con la cookie que actualiza el navegador.

Se inspeccionaron los JAR locales de Spring Security **7.1.1** con `javap` de JDK **21.0.8**:

```powershell
$javap = 'C:/Program Files/Eclipse Adoptium/jdk-21.0.8.9-hotspot/bin/javap.exe'
& $javap -c -p -classpath C:/Users/limas/.m2/repository/org/springframework/security/spring-security-config/7.1.1/spring-security-config-7.1.1.jar org.springframework.security.config.annotation.web.configurers.CsrfConfigurer
& $javap -c -classpath C:/Users/limas/.m2/repository/org/springframework/security/spring-security-web/7.1.1/spring-security-web-7.1.1.jar org.springframework.security.web.authentication.session.NullAuthenticatedSessionStrategy org.springframework.security.web.csrf.CookieCsrfTokenRepository
```

API verificada: `CsrfConfigurer.sessionAuthenticationStrategy(SessionAuthenticationStrategy)`; `getSessionAuthenticationStrategy()` devuelve la estrategia configurada antes de crear la predeterminada `CsrfAuthenticationStrategy`. `configure()` la añade mediante `SessionManagementConfigurer.addSessionAuthenticationStrategy`. `NullAuthenticatedSessionStrategy.onAuthentication(...)` solo retorna: basta sustituir la estrategia del configurador CSRF; no hace falta cambiar la política STATELESS ni la estrategia global de sesiones.

También se verificó `CookieCsrfTokenRepository.saveToken(null, request, response)`: emite cookie vacía con Max-Age=0 y aplica el mismo `cookieCustomizer`; la siguiente petición sin cookie genera un token mediante el manejador SPA.

## Regresión antes de la corrección

Nueve casos en el contexto existente de `AuthIT`, sin otro pool: GET autenticados sin renovación ni log de reemplazo; escritura con cabecera inicial tras aplicar cada Set-Cookie como un navegador; invalidación y emisión posterior en registro/login/logout; rechazo sin cabecera o con cabecera incorrecta con sesión válida.

Antes de ejecutar se comprobaron puertos 8080/18034 libres y ausencia de `frontend/tmp/e2e.lock` y del lock de diagnóstico (solo existencia, sin leer ni modificar su contenido).
