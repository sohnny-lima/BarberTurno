## Implementación

- `scheduling/BloqueoController`, `BloqueoService` y DTO `BloqueoDto`,
  `CrearBloqueoDto`, `CrearBloqueosLoteDto`: GET/POST de
  `/api/barberos/{id}/bloqueos`, POST `/api/bloqueos/lote` y DELETE
  `/api/bloqueos/{id}` según arquitectura §6.3. Lectura ADMIN o BARBERO asignado;
  perfiles ajenos, incluso inexistentes, devuelven 404. Escrituras solo ADMIN
  con CSRF. El DTO devuelve exclusivamente id, barberoId, inicio, fin y motivo;
  las fechas salen con desfase de Lima mediante `TiempoNegocio`.
- GET consulta solapes del rango inclusivo de fechas en Lima convertido a
  `[inicioDelDia(desde), finDelDia(hasta))`, ordenados por inicio e id. El rango
  invertido, de más de 366 días inclusivos o cuyo último día no admite una
  medianoche siguiente devuelve 400 `RANGO_FECHAS_INVALIDO`. Parámetros ausentes
  o ilegibles siguen el manejador común 400 `VALIDACION`.
- DTO record con Bean Validation: inicio y fin obligatorios y con desfase;
  motivo no blanco de 3–200 caracteres; lote no vacío, ids positivos y no
  nulos. Duplicados → 400 `VALIDACION`, con campo `barberoIds`; cualquier perfil
  inexistente → 404 y ninguna inserción. `inicio >= fin` → 400
  `INTERVALO_INVALIDO`; inicio anterior a Clock → 422 `INICIO_EN_PASADO`.
- Altas transaccionales: comprobar intervalo → una llamada a
  `barberoRepository.bloquearPorIds(ids)` (②) con ids ordenados → comprobar
  existencia de todos → capturar Clock después de la espera → buscar reservas
  ocupantes que solapan `[inicio, fin)` de cada perfil → solo si no hay conflictos,
  insertar todos con `saveAllAndFlush`. Se reutiliza `ReservaRepository`, sin
  dependencias entre servicios ni bloqueo ③. Todos los estados salvo CANCELADA
  ocupan franja, incluidos terminales y reservas que ya comenzaron.
- 409 individual incluye `reservas: [ids]`; 409 de lote incluye
  `reservas: {"barberoId": [ids]}` con todos los perfiles en conflicto. No hay
  inserciones parciales ni cambios en reservas. Respuesta 201 de lote ordenada
  por id de perfil. `creado_por` es el actor revalidado de la sesión y `creado_en`
  es el mismo instante del Clock para todo el lote.
- DELETE obtiene el id de perfil con una proyección nueva en `BloqueoRepository`,
  toma ②, vuelve a buscar el bloqueo y lo borra físicamente RN-16 con flush.
  Devuelve 204 sin cuerpo; si falta o desapareció durante la espera, 404.
- `SecurityConfig` habilita exclusivamente las cuatro rutas por rol y método;
  conserva `DEFAULT_CSRF_MATCHER`, el filtro de contraseña temporal y `denyAll`.
  `BarberoIT` conserva su guardia de rutas pendientes usando disponibilidad.
- Javadoc útil añadido a ambos componentes, constructores y métodos públicos,
  a los tres records y su fábrica, y a la proyección de repositorio. Javadoc
  de `Jornada` explica el mapeo JDBC directo; la configuración de seguridad
  modificada conserva documentación de sus permisos y CSRF.

Decisiones menores: 366 días cuentan ambos extremos; el listado incluye
cualquier bloqueo que se cruza con el rango, aunque haya empezado antes.
Se admiten perfiles inactivos sin reactivarlos, como las jornadas. Los bloqueos
pueden solaparse entre sí, ya que RN-18 únicamente prohíbe cruzar reservas.
Se conserva el motivo recibido tras validarlo, sin reinterpretar el texto.
La comparación con el reloj ocurre después de adquirir ② para respetar RN-18
también si el inicio pasó durante la espera. Sin cambios de contratos, DDL,
reglas, criterios, dependencias ni arranque; README intacto por alcance.

## Hallazgo de implementación corregido

La carrera exigida descubrió un defecto previo del mapeo de `Jornada`:
`hibernate.jdbc.time_zone=UTC` junto con el puente `java.sql.Time` desplazaba
las horas locales en Windows (zona Lima). El PUT válido `08:00–19:00` devolvía
409 `CONFLICTO`, SQLState **23514**, restricción **jornada_intervalo_valido**:
el desplazamiento de cinco horas hacía que el fin cruzara medianoche.
No era un interbloqueo ni un conflicto con reservas.

Corrección local en `Jornada.java`: `@JdbcTypeCode(SqlTypes.LOCAL_TIME)` en
ambos campos para usar JDBC 4.2 directamente con `LocalTime`. Se conservan el
tipo de dominio, las columnas `time`, la zona JDBC para instantes y los contratos.
Javadoc actualizado. Regresiones verifican respuesta y valores físicos SQL
de `00:00–01:00`, `18:30–19:30`, `23:00–23:59`, además de `08:00–19:00`
en ambas carreras; JornadaIT conserva sus 48 casos.

Hallazgo para el arquitecto: revisar si se llegaron a configurar jornadas
locales con la implementación anterior de T-15, cuyo contenido físico puede
estar desplazado. No se inspeccionó ni reescribió la BD de desarrollo ni se
creó una migración de datos. No requiere cambiar el diseño documentado.
