## Hallazgo H-084-01: fichas activas en una operación global

El backlog §8.2.8 exige que `GET /api/mis-negocios` liste **membresías activas y fichas activas** de la cuenta autenticada, leyendo `membresia` y `vinculo_cliente` mediante una operación propia de la cuenta. §8.1 exige que las operaciones globales no tengan negocio: proveedor vacío y acceso a tablas de negocio cerrado por RLS. La lectura de §8.2.8 no puede distinguir las fichas activas con el índice actual:

- `V102__ficha_cliente.sql` crea `vinculo_cliente` con solo `(negocio_id, usuario_id)`. No tiene `activo`.
- `mantener_vinculo_cliente()` conserva el vínculo incluso al desactivar la ficha. Es necesario conservar esa información para la protección de identidad compartida: `VinculoClienteRepository.existeEnOtroNegocio` especifica expresamente «incluso inactiva» (V2-DA-28 y V2-RN-16).
- `cliente.activo` sí cambia, pero `cliente` tiene RLS `ENABLE` y `FORCE`. Con el contexto vacío de una operación global, consultar o unir esa tabla devuelve cero fichas, también para una ficha activa de la cuenta.
- La única migración autorizada para V2-05, `V106__indices_negocio.sql`, añade índices de acceso; no incluye un cambio del índice de plataforma o de su disparador.

No se ha implementado una respuesta incorrecta ni se han omitido fichas activas, incluido fichas inactivas, cambiado el contexto de una operación global o eludido RLS para resolverlo. No se afirma una explotación de permisos: el hallazgo es la incompatibilidad entre el contrato exigido, las fuentes de datos autorizadas y el diseño actual.

**Decisión necesaria del arquitecto:** concretar cómo puede conocer esta operación global el estado activo de las fichas. Una opción es ampliar aditivamente la proyección de plataforma y su disparador con el estado, conservando los vínculos inactivos para V2-RN-16; otra requiere especificar un mecanismo de consulta autorizada y conciliarlo con el contexto vacío obligatorio de §8.1. Son alternativas de diseño, no cambios aplicados. No se debe borrar el vínculo al desactivar ni editar V102 aplicada. Si se elige modificar DDL, habrá que asignar y autorizar la migración correspondiente.

La parada se basa en AGENTS §4: «Codex debe parar y marcar la tarea como `Bloqueada (motivo)` cuando […] haya que cambiar un contrato de API (§6 de arquitectura), el DDL (§5), una regla RN o un criterio de aceptación». El estado se registra en `10-backlog.md` §4 conforme a AGENTS §5.1 y al encargo, sin modificar `docs/tareas.md` de v1. No se cierra ninguno de los pasos 1…5 ni se declara la tarea Hecha.

import java.util.UUID;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;

import org.springframework.test.annotation.DirtiesContext;

import static org.assertj.core.api.Assertions.assertThat;

/** Diagnóstico del bloqueo de V2-05; toda escritura termina en rollback de la prueba. */

                select count(*) from pg_class
                where relowner=(select oid from pg_roles where rolname=current_user)
                """, Integer.class)).isZero();
        assertThat(jdbc.queryForObject("""
                select relrowsecurity and relforcerowsecurity
                from pg_class where oid='cliente'::regclass
                """, Boolean.class)).isTrue();
        assertThat(jdbc.queryForList("""
                select column_name from information_schema.columns
                where table_schema='public' and table_name='vinculo_cliente'
                order by ordinal_position
                """, String.class)).containsExactly("negocio_id", "usuario_id");

        jdbc.queryForObject("select set_config('app.negocio_id', '1', true)", String.class);
        long cuenta = jdbc.queryForObject("""
                insert into usuario (nombre, correo, telefono, password_hash, rol,
                    privacidad_aceptada_en, creado_en, actualizado_en)
